## Readable Code

### 코드 
코드는 코드 쓰는 시간보다 읽는 시간이 휠씬 많다. 
그래서 코드는 현재가 아니라 미래를 위해서 읽기 좋은 코드를 작성해야한다.
따라서 코드는 읽기가 좋아야하고 유지보수하기 좋아야한다.
코드가 잘 읽히는다는것은 "이해가 잘되는것"이고 유지보수하기가 수월하며 시간과 자원이 절약된다는 의미이다.

### 용어 정리
- 도메인: 해결하고자 하는 문제 영역
- 도메인 지식: 도메인을 이해하고 해결하는 데 필요한 지식
- 레거시, 유산: 우리가 현재 가지고 있는 코드
- 조상: 과거의 나, 과거의 동료
- 후손: 미래의 나, 미래의 동료
- 프로그램: 프로그램은 데이터 + 코드 이다. (데이터는 추상화를 통해 리펙토링하고 코드를 인지적 경제성으로 리펙토링하는것이 중요하다.)

## 추상 (뽑을 추, 코끼리 상, 형상 상))

추상이란 어떤 것에 **중요한 부분만 선택**하고 **다른 측면을 버린다**는 것을 말한다.

컴퓨터는 0과 1만 알지만 추상화를 잘하여 높은 고도의 일을 수행한다.
이렇게 추상화를 중요하고 추상화에 따라서 할 수 있는 일이 다양해진다.

`추상화를 잘하면 복잡한 데이터와 복잡한 로직을 단순화하여 이해하기 쉽도록 돕는다.`

#### 추상화를 통해서 구체 유추가 중요한 이유

자동차를 "바퀴 달린 것"으로만 표현하면 다른 사람들은 이해하기 어려울 수 있다.
이해가 어려운 이유 잘못된 추상화하여 중요한 정보와 문맥을 제거했기 때문이다.

적절한 추상 특징
1. 추상화 과정에서 중요한 정보를 부각시킨다.
2. 해석자가 동일하게 공유하는 문맥(Context)을 공유할 수 있다.
즉, 적절한 추상화는 도메인의 문맥(context)안에서, 정말 중요한 핵심 개념만 남겨서 표현한것을 말한다.

대표적 추상의 행위
1. 이름을 짓기
   - 단수와 복수 구분하기 -(e)s or 집합 명사 사용하기
   - 이름 줄이지 않기
   - 은어/방언 사용하지 않기 -> 새로운 팀원이 합류하면 이 용어를 단번에 이해할 수 있는가?
   - 도메인 용어 사용하기 -> 도메인 용어 사전이 있어야한다.
   - 좋은 코드를 보고 습득하면 좋다.
2. 메서드 :: 한 문단에 글의 주제는 하나다. 
   - 메서드에 여러 내용과 동작이 들어가면 안된다.
   - 메서드명
     - 메서드명도 하나의 의미를 담는 내용으로 작성되어야한다. 
     - 추상화된 구체를 유추할 수 있는, 적절한 의미가 담긴 이름어야한다.
     - 파라미터와 연결지어 더 풍부한 의미를 전달할 수 도 있다.
   - 파라미터
     - 파라미터는 외부 세계와 소통하는 창이다.
     - 파라미터의 타입, 개수, 순서를 통해 의미를 전달한다.
   - 반환 타입
     - 메서드 시그니처에 납득이 가는, 적절한 타입의 반환값 돌려줘야한다.
     - void 대신 충분한 반환할 만한 값이 있는지 고민하고 반환값이 있다면 반환하는것이 메서드를 테스트하기 더 쉬워진다.
   - 추상화 레벨
     - 하나의 메서드안에서는 추상화 레벨이 동등해야한다. 
3. 매직 넘버, 매직 스트링
   - 의미를 갖고 있으나 상수로 추출되지 않는 숫자, 문자열을 말한다.
   - 상수로 추출하여 이름을 짓고 의미를 부여하여 가독성과 유지보수성을 높힌다.

## 논리, 사고의 흐름을 더 읽기 쉽게
사람은 뇌(메모리)에 적은 정보를 올려둘 수록 이해하기가 쉽다. </br>
즉 읽기 좋은 코드는 뇌 메모리를 적게 사용해야한다. 한 단어로 표현하면 인지적 경제성이라고 할 수 있다. </br> 

방법
1. Early Return를 사용하여 else문 사용을 지양하자. Early Return을 사용하면 Return후 Return 이전의 코등에 대해서 기억할 필요없어진다.
2. 사고의 Depth 줄이기
   - 중첩 분기문, 중첩 반복문
     - 무조건 1 Depth로 만들어라가 아니다. **중요한것은 사고의 Depth를 줄이거는것이 중요하다. 2Depth가 읽기 좋으면 그대로 둬라.**
   - 사용할 변수는 가깝게 선언하기
3. 공백 라인도 의미를 가진다.
   - 복잡한 로직의 의미 단위를 나누어 보여줌으로써 읽는 사람에게 추가적 정보를 전달한다.
4. ! not 연산자를 피하자. ! 연산자를 가속성이 떨어진다.
   - 부정어구를 쓰지 않아도 되는 상황인지 체크하기
   - 부정의 의미를 담은 다른 단어가 존재하는지 고민하기
   - 예:: !isLeftDirection -> isRightDirection 이나 isNotLeftDirection 리펙토링
5. 해피 케이스와 예외 처리
   - 예외가 발생할 가능성 낮추기
   - 어떤 값의 검증이 필요한 부분은 주로 외부 세계에서 데이터가 넘어올때
     - 사용자 입력, 객체 생성자, 외부 서버의 요청 등
   - 의도한 예외와 예상하지 못한 예외를 구분하기
     - 사용자에게 보여줄 예외와, 개발자가 보고 처리해야 할 예외 구분
   - null을 대하는 자세
     - 항상 NullPointException을 방지하는 방향으로 경각심 가지기
     - 메서드 설계시 return null을 하지 않고 Optional객체를 리턴하는것이 좋다.
       - Optional의 간단한 내용
         - Optional은 비싼 객체이다.
         - Optional이 파라미터로 받지 않도록한다.
         - Optional을 반환받았다면 최대한 빠르게 해소한다.

## 객체

1. 협력과 책임
2. 캡상추다
3. 관심사의 분리: 높은 응집도, 낮은 결합도(A가 변경되었을때 B도 변경되면 A와 B는 응집도가 높은것이고 관심사의 분리가 제대로 되었는지 살펴봐야한다.)

객체로 추상화하기
1. 비공개 필드(데이터), 비공개 로직(코드)
2. 공개 메서드 선언부를 통해 외부 세계와 소통
3. 객체의 책임이 나뉨에 따라 객체 간 협력이 발생

객체가 제공하는것
1. 절차 지향에서 보이지 않던 개념을 가시화
2. 관심사가 한 군데로 모이기 때문에 유지보수성 증가
3. 여러 객체를 사용하는 입장에서는 구체적인 구현에 신경쓰지 않고 보다 높은 추상화 레벨에서 도메인 로직을 다룰 수 있다

새로운 객체를 만들 때 주의할 점
1. 1개의 관심사로 명확하게 책임이 정의되었는지 확인하기
2. 생성자, 정적 팩토리 메서드에서 유효성 검증이 가능하다. -> 도메인 특화된 검증 로직이 들어갈 수 있다
3. setter 사용 자제, 데이터는 불변이 최고이다. setter보다는 update와 같이 의도를 드러내는 네이밍을 고려하자
4. getter도 처음에는 사용 자제하고 객체에 물어보기
5. 필드의 수는 적으면 적을수록 좋다

### SOLID
1. SRP: Single Responsibility Principle(단일 책임 원칙: 하나의 클래스는 단 한 가지의 변경 이유만을 가져야한다.)
   - "변경 이유" = 책임
   - 객체가 가진 공개 메서드, 필드, 상수 등은 해당 객체의 단일 책임에 의해서만 변경 되는가?
   - 관심사의 분리
   - 높은 응집도, 낮은 결합도
2. OCP: Open-Closed Principle(개방-폐쇄 원칙: 확장에는 열려있고 수정에는 닫혀있어야한다.)
   - 새로운 요구 사항이 있을때 코드가 과도하게 변경되면 OCP를 지키지 못하고 있을 확률이 높다. 
   - 추상화와 다형성을 활용해서 OCP를 지킬 수 있다.
3. LSP: Liskov Substitution Principle(리스코프 치환 원칙: 상속 구조에서 부모 클래스의 인터스턴스를 자식 클래스의 인스턴스로 치환할 수 있어야한다.)
   - 자식 클래스는 부모 클래스의 책임을 준수하며, 부모 클래스의 행동을 변경하지 않아야한다.
   - LSP를 위반하면, 상속 클래스를 사용할때 오동작, 예상 밖의 예외가 발생 등을 방지하기 위한 불필요한 타입 체크 로직(instanceof)이 추가로 동반될 수 있다.
   - 상속 구조에서는 instanceof등으로 타입을 체크해서 예외적으로 처리하지 않아야 정상적이다.
4. ISP: Interface Segregation Principle(인터페이스 분리 원칙)
    - 클라이언트는 자신이 사용하지 않는 인터페이스에 의존하면 안된다. -> 즉, 인터페이스를 잘게 쪼개라
        - ex) 인터페이스에 메서드가 5개가있는데 3개는 쓰는거지만 2개는 쓰지 않고 다른 구현체에서 필요한 경우
    - ISP를 위반하면, 불필요한 의존성으로 인해 결합도가 높아지고, 특정 기능의 변경이 여러 클래스에 영향을 미칠 수 있다.
5. DIP: Dependency Inversion Principle
